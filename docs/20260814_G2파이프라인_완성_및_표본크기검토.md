# G2 파이프라인 완성 및 표본 크기 검토

작성 2026-08-14 · 관련 `20260810_MediaPipe_실영상검증.md`, `20260810_IRB_확인_및_준비.md`

---

## 결론

**촬영부터 G3 분석까지 전 구간이 관통한다.**

```
폰 mp4     -> mediapipe_pose.py  -> 지표 JSON  ┐
                                              ├-> pair_trials.py -> phase3_agreement.py
Kinect mkv -> kinect_playback.py -> 지표 JSON  ┘
```

1 trial 로 끝까지 확인했다. IRB 회신이 오면 바로 수집에 들어갈 수 있다.

그 과정에서 **잠재 버그 3건**을 잡았고, **표본 크기 문제**를 정량적으로 확인했다(§5). 후자가 오늘 가장 중요한 발견이다 — **계획서의 10명 목표로도 G3 기준을 만족할 확률이 29%다.**

---

## 1. 새로 만든 것

| 파일 | 역할 |
|---|---|
| `scripts/kinect_playback.py` | mkv 오프라인 body tracking. 32 joint → BODY_25 투영 |
| `scripts/pair_trials.py` | 폰·Kinect 짝짓기 + 동기화 QC + 짝 CSV 생성 |
| `scripts/phase3_agreement.py` | ICC(2,1)·Bland-Altman·RMSE. 자체 검증 5/5 |
| `sts_metrics.auto_trim()` | 준비·정리 구간 자동 제거 |

`kinect_playback.py` 의 핵심은 Kinect 32 joint 를 **BODY_25 호환 (프레임, 75) 로 투영**하는 것이다. 폰과 **같은 `sts_metrics.py`** 를 통과시키므로, 지표 차이가 곧 장비 차이가 된다.

> 재생 모드에서는 `Device.calibration` 이 없다. `pykinect.start_body_tracker()` 는 라이브 전용이므로 녹화본에서 캘리브레이션을 직접 가져와 `Tracker` 를 만들어야 한다.

## 2. 동기화 — 박수 소리는 쓸 수 없다

**`k4arecorder` 에는 오디오 옵션이 없고, mkv 트랙 구성도 color/depth/IR/IMU 뿐이다.** Kinect 녹화에는 소리가 없다.

계획서 §3.3이 **코 수직 궤적 교차상관을 주 방법**으로, 박수를 교차 확인용으로 둔 것이 다행이다. 주 방법이 그대로 살아 있다.

### 전체 신호로 상관을 걸면 틀린다

| 방법 | 추정 시차 | 상관 피크 |
|---|---|---|
| 전체 신호 | **+57.43초** ← 폰 영상 전체가 62초인데 말이 안 된다 | 0.348 |
| **활동 구간끼리** | **+13.47초** | **0.958** |

준비·정리 구간과 미검출 보간 램프가 상관을 지배한다. `auto_trim` 으로 활동 구간을 먼저 잡고 그 안에서 맞춰야 한다. 트리밍 기반 추정(+13.73초)과도 일치한다.

### 판정 기준 — 비율을 쓰면 안 된다

STS 는 주기 신호라 **한 주기씩 밀린 위치에서도 상관이 높다.** 배경 99백분위가 0.814로 높게 나와 피크/배경 비가 1.18배에 그친다. 따라서 **피크의 절대값(≥0.5)과 활동 구간 길이 일치**로 판정한다.

같은 이유로 **미세 정렬은 주기의 정수배만큼 모호하다.** trial 짝짓기 QC 로는 충분하지만, 프레임 단위 정렬이 필요하면 **손목이 모이는 박수 동작**을 따로 검출해야 한다.

> **G3 에는 프레임 단위 동기화가 필요 없다.** 총 시간·각도 범위 같은 trial 단위 요약값을 비교하기 때문이다. 동기화는 "두 장비가 같은 trial 을 찍었는가"의 QC 수단이다.

## 3. 잡은 버그 3건

### ① 준비 구간이 국면 분할을 통째로 실패시킨다

62초 영상에서 실제 동작은 25.5~36초 **10초뿐**이었다. STS 봉우리 0.4 vs 전체 범위 3.4, 검출 문턱 1.7 → **0회 검출**.

`auto_trim()` 으로 자동화했다. 논문이 49명에게 `tofix` crop 을 손으로 지정한 것과 같은 문제다.

만드는 과정에서 두 번 틀렸다. **드리프트를 안 빼면** 미검출 보간 램프가 더 큰 표준편차를 내어 엉뚱한 구간을 잡고, **공백을 안 이으면** 반복 사이 정지 때문에 4.63초만 남는다(5회가 4.5초면 불가능하니 바로 걸렸다).

### ② 국면 분할 휴리스틱 일반화가 논문 재현을 깨뜨렸다

원 코드의 착석 보완 조건이 `ups == 4` 또는 `5` 로 하드코딩돼 6회에서 동작하지 않았다. `downs <= ups` 로 일반화하자 —

```
time            r 1.0000 -> 0.9761
right_knee_max  r 1.0000 -> 0.8932
```

**5회 데이터에도 영향이 있었다.** 기본값은 원 코드 그대로 두고 반복 수를 아는 자체 데이터에서만 켜도록 인자화했다. 재검증으로 217명 13지표 r=1.0000 복구.

> 회귀 검증을 안 돌렸으면 G1이 깨진 줄 모르고 갔을 것이다. **파이프라인을 건드릴 때마다 `--validate` 를 돌린다.**

### ③ 픽셀 전제의 좌표 필터가 Kinect mm 좌표를 지운다

논문의 `res[res < 0.5] = NaN` 은 배열 전체에 걸린다. OpenPose 픽셀 좌표는 항상 양수라 사실상 신뢰도 열만 걸러진다.

**Kinect 는 카메라 중심 기준 mm 라 음수가 나온다.** 실측 x 범위가 −1011 ~ −110mm 로 **전부 음수**였다. 그대로 적용하면 x 가 통째로 NaN 이 되고 보간이 채워 **그럴싸하지만 틀린 값**이 나온다.

이번 자료는 방향 판정이 `L` 로 나와 X 반전이 먼저 걸리면서 **우연히** 살아났다(손실 0.0%p). 피험자가 카메라 반대쪽에 서면 `R` 로 판정되어 그대로 터진다. `filter_all=False` 로 신뢰도 열만 거르도록 분리했다.

## 5. 표본 크기 — 오늘 가장 중요한 발견

참 ICC 0.85 인 상황을 400회 반복 시뮬레이션했다(`phase3_agreement.icc21` 사용).

| 대상 수 | ICC 평균 | CI 폭 중위 | CI 하한 중위 | **하한>0.60 달성률** |
|---|---|---|---|---|
| 2 | **추정 불가** | — | — | — |
| **3** | 0.663 | **1.214** | −0.222 | **5%** |
| 5 | 0.778 | 0.868 | 0.111 | 15% |
| 8 | 0.820 | 0.511 | 0.459 | 30% |
| **10** | 0.813 | 0.467 | 0.495 | **29%** |
| 15 | 0.827 | 0.347 | 0.599 | 50% |
| 20 | 0.839 | 0.273 | 0.667 | 67% |
| 30 | 0.838 | 0.222 | 0.703 | 84% |

계획서 G3 기준은 `ICC 0.80 의 95% CI 하한을 0.60 이상으로 보이는 것`이다.

### 읽히는 것 두 가지

**① 2명으로는 ICC 계산 자체가 안 된다.** 대상 간 분산을 추정할 자유도가 없다.

**② 3명은 ICC 가 0.663 으로 하향 편향되고 CI 폭이 1.2다.** 사실상 무정보다. 달성률 5%.

**③ 계획서의 10명 목표도 달성률이 29%다.** 원 계획 자체가 낙관적이었다. 기준을 만족하려면 20~30명이 필요한데, 7주 학부 연구에서 현실적이지 않다.

> **주의** — 위는 **대상 수** 기준이다. "10명 × 3 trial = 30" 을 30 관측으로 넣으면 ICC 가 부풀려진다. 같은 사람의 반복은 독립이 아니기 때문이다. 팀 문서 §해석 기준 4번이 지적한 것과 같은 문제다.

## 6. 2~3명으로 갈 경우의 설계 전환

**ICC 를 주 결과로 쓸 수 없다.** 대신 아래로 전환한다. 계획서 §6의 `G2 미달 → 축소 분석` 경로에 해당한다.

| 원 계획 | 전환안 | 근거 |
|---|---|---|
| ICC(2,1) 등급 확정 | **참고값으로만 보고**, 신뢰구간 폭을 명시 | §5 |
| — | **Bland-Altman 편향·LoA 중심** | 관측 수에 의존하므로 trial 을 늘리면 개선된다 |
| — | **장비별 재현성(test-retest)** | 같은 사람 반복이므로 대상 수가 적어도 성립한다 |
| 사전등록 등급 확정 | **방향 예측 적중 여부만** 확인 | 등급 확정은 후속 과제로 |

### 왜 이 전환이 방어 가능한가

- **Bland-Altman 은 원래 소표본 방법 비교용**으로 제안된 것이다. LoA 는 관측 수로 좁아지므로 **3명 × 10 trial = 30 관측**이면 쓸만해진다(참여자 내 상관 때문에 유효 표본은 30보다 작다는 점은 명시)
- **재현성은 다른 질문이지만 유용하다.** "스마트폰으로 세 번 재면 얼마나 일관된가"는 실사용에 직결된다. 이미 예비 데이터가 있다(3회 반복 CV: `trunk_lean_max` 0.4%, 비대칭 84~90%)
- 사전등록 기대치표는 **"각도는 잘 맞고 비대칭은 못 쓴다"는 방향 예측**을 담고 있다. 방향이 맞았는지는 소표본에서도 확인된다

### 실무 권고

**사람 수를 못 늘리면 1인당 trial 수를 늘린다.**

```
3명 × 10 trial = 30 관측     촬영 약 1시간 (1인당 20분)
```

ICC 는 개선되지 않지만 **Bland-Altman 의 LoA 는 좁아진다.** 그리고 재현성 분석의 표본이 된다.

### 남는 한계 — 반드시 명시할 것

- **연령·체격 다양성 없음.** 20대 팀원만으로는 고령층 일반화 불가. 이건 원래 있던 한계다
- **대상 수 부족으로 ICC 등급 확정 불가.** G3 를 "등급 확정"이 아니라 **"오차 크기 기술"** 로 축소
- 최종 보고서에서 `n=3 예비 타당도 연구`로 명시

## 8. 재현

이 문서의 1 trial 은 **예비 실험**이며, 2026-08-17 랩실 본촬영과 구분하려고
산출물에 `S1` 세션 표시를 붙였다(`20260817_G2_2차세션_촬영_및_분석.md` 참조).

```bash
python scripts/mediapipe_pose.py  test_videos/phone/P01_T01.mp4  --zero-lag --reps 5 \
       --save results/g2_phone_P01_S1_T01.npy --json results/g2_phone_P01_S1_T01.json
python scripts/kinect_playback.py test_videos/kinect/P01_T01.mkv --reps 5
python scripts/pair_trials.py --phone results/g2_phone_P01_S1_T01.npy \
       --kinect results/P01_S1_T01_kinect.npy \
       --phone-json results/g2_phone_P01_S1_T01.json \
       --kinect-json results/P01_S1_T01_kinect.json \
       --subject P01 --id S1_T01 --out results/g2_pairs_P01_S1_T01.csv
python scripts/phase3_agreement.py --pairs results/g2_pairs_P01_S1_T01.csv
```

> `kinect_playback.py` 는 입력 mkv 이름을 따라 출력한다. 위 `S1` 이름을 얻으려면
> mkv 를 `P01_S1_T01.mkv` 로 두거나, 산출물을 뒤에 바꿔 준다.
>
> `phase3_agreement.py` 는 **`--plot` 과 무관하게 결과 CSV·txt 를 항상
> `results/phase3/` 에 쓴다.** 다른 세션을 분석할 때 이 경로가 덮이므로,
> 실행 뒤 산출물을 목적지로 옮기고 커밋본을 복원할 것.

파이프라인을 수정했다면 **반드시** 회귀 검증을 돌린다.

```bash
python scripts/sts_metrics.py --validate --n 400     # 217명 13지표 r=1.0000 유지 확인
python scripts/phase3_agreement.py --selftest        # 5/5 통과 확인
```
