## G0 시도 기록 — 2026-08-08 (2차)

### 결론: **케이블 문제로 확정. 전원·경로·PC·소프트웨어 전부 무혐의.**

Kinect 뒷면 LED **흰색 깜빡임** = MS 공식 표의 `전원은 켜졌으나 USB 3.0 데이터 연결 없음`.

### 관측된 열거 상태 (3회 시도 모두 동일)

MS 문서의 내부 엔드포인트 5개 중 **High Speed 쪽만 붙고 SuperSpeed 쪽은 전부 실패**했다.

| PID | 구성요소 | 속도 | 결과 |
|---|---|---|---|
| `097B` | USB 2.0 Hub | HS | ✅ |
| `097E` | Microphones | HS | ✅ |
| `097A` | USB3.1 Gen2 Hub (메인) | SS | ❌ |
| `097C` | Depth 카메라 | USB3.0 | ❌ |
| `097D` | Color 카메라 | USB3.0 | ❌ |

카메라 2개는 `USB\VID_0000&PID_0006` (**잘못된 구성 설명자**, `CM_PROB_FAILED_POST_START`) 형태의 stub으로 나타난다. 부모는 Kinect 내부 허브 `097B`의 포트 1·2다. **켜져서 열거를 시도하다 SuperSpeed가 없어 실패하는 상태**이며, Kinect 카메라는 USB 2.0으로 폴백하지 않는다.

`k4arecorder --list` → `Unable to open LIBUSB at index 0` → `Device Open Failed`.

### 3회 시도 대조

| 시도 | 케이블 | 접속 경로 | 결과 |
|---|---|---|---|
| 1 | C-to-C (사제) | `Parent=VID_214B&PID_7260` — **4-Port USB 2.0 허브 경유** | SS 실패 |
| 2 | C-to-A (편의점) | `Parent=ROOT_HUB30`, Port_#0015 — 직결 | SS 실패 |
| 3 | C-to-C (사제) | `Parent=ROOT_HUB30`, Port_#0011 — 직결 | SS 실패 |

**서로 다른 케이블 2개 × 서로 다른 포트 3곳, 그중 2회는 루트 허브 직결인데도 동일 실패.** 경로는 배제된다.

### 배제된 원인

| 원인 | 배제 근거 |
|---|---|
| 전원 부족 | LED **흰색**(주황 아님). 카메라가 열거를 시도함 |
| 허브 경유 | 시도 2·3은 `ROOT_HUB30` 직결 |
| PC USB 3.0 불량 | `일반 SuperSpeed USB 허브`(ASMedia `VID_174C`) 정상 열거, USB 3.0 루트 허브 4개 전부 OK |
| SDK·드라이버 | `initialize_libraries(track_body=True)` 성공, `K4ABT_JOINT_COUNT=32` |

### 확정된 원인

**보유 케이블 2개가 모두 USB 2.0 전용(충전용)이다.** SuperSpeed 신호선 4가닥이 물리적으로 없다.
**두 케이블 모두 Kinect 동봉품이 아니다** — 수령 목록의 `데이터 케이블 (PC 연결용) ✅` 기록과 불일치. §하드웨어 구성 참조.

### 필요한 것

| 항목 | 사양 |
|---|---|
| 케이블 | `USB 3.0` / `USB 3.2 Gen1` / `SuperSpeed` / `5Gbps` 표기 필수. A쪽 단자 **혀 파란색·핀 9개**, SS 로고. 1m 내외(패시브는 1.5m 미만) |
| 포트 | PC **후면 파란색 USB-A** 직결 |
| 전원 | C-to-A 사용 시 벽 전원 **필수**. 아무 **5V 2A USB-A 충전기** + 동봉 배럴 케이블. **돼지코 불필요** |

> **돼지코가 필요 없는 이유**: MS 1624는 USB-A 출력 소켓이 달린 평범한 5V 충전기이고, 동봉 전원 케이블이 `USB-A → 배럴`이다. 따라서 한국 플러그 5V USB-A 충전기 아무거나로 대체된다.

### 미해결 잔여 위험

검증된 USB 3.0 케이블 + 벽 전원으로도 `097A/097C/097D`가 뜨지 않으면 **본체 SuperSpeed 하드웨어 고장**이다. 대여 장비이므로 **반납 기한 전에 확정할 것.** 고장 확정 시 계획서 §6의 `G0 실패 → 스마트폰 단독 + 공개 데이터로 설계 축소` 경로를 발동한다.

→ **2026-08-09 해소됨. 하드웨어 고장 아니었다.** 아래 참조.

### `verify_kinect.py` 실제 버그 — 수정 완료

문서가 예고한 "하드웨어 없이 작성돼 첫 실행 시 오류 가능"이 실제로 발생했다.

**증상**

```
k4a_image_t_get_context(). Invalid k4a_image_t 0000000000000000
[K4ABT] DepthFrameBlobK4A.cpp: Get depth buffer from the capture handle failed!
[K4ABT] TrackerHost.cpp: EnqueueCapture(). Initialize DepthFrameBlob failed!
-> Body tracker capture enqueue failed!
```

**원인**: `pykinect.default_configuration` 의 **`synchronized_images_only` 기본값이 `False`** 다. 이 경우 capture 에 color 만 담기고 depth 가 빠질 수 있는데, body tracker 는 매 capture 에 depth 를 요구한다.

**수정**: `config.synchronized_images_only = True` 추가. 실측으로 30/30 프레임에 depth 가 들어옴을 확인했다. 추가로 depth 없는 capture 를 거르는 방어 코드와 `--delay` 옵션(카메라 앞으로 이동할 시간)을 넣었다.

> **DirectML 검증됨.** `K4ABT_TRACKER_PROCESSING_MODE_GPU_DIRECTML` 로 트래커가 RTX 5060 에서 정상 기동했다. 환경구축 기록 §2의 "CUDA 대신 DirectML" 결정이 실측으로 확인된 것이다.
> 단 8.7 fps / 106ms 는 GPU 치고 느려 CPU 폴백 가능성이 있다. 오프라인 처리 방식이라 수집을 제약하지 않으므로 G0 통과 후 확인한다.

### 인체 검출 0 의 원인 — 촬영 조건

Color/Depth 스냅샷을 떠서 확인했다. 장비가 아니라 프레임 구성 문제다.

| # | 문제 | 근거 |
|---|---|---|
| 1 | **하반신이 책상에 잘림** | 앉은 자세 + 책상이 프레임 하단 차단. 무릎·발목·발 부재 = `STS_JOINTS` 핵심 관절 전부 없음 |
| 2 | **거리 근접 한계** | depth 중위 **1531mm**. 권장 1.5~3m 의 하한 |
| 3 | **역광이 depth 를 파괴** | 유리문 햇빛이 ToF IR 센서를 포화시킴. depth 유효화소 **21%**, `3000-3860mm` 구간 **0.0%** (문 영역 통째로 소실) |

**조치**: ① 일어서서 2~2.5m 뒤로 ② 카메라를 빼거나 높여 발까지 프레임에 ③ 유리문 커튼 차단.

> ③은 Phase 2 본촬영에도 적용된다. 계획서 §3.3의 "밝은 실내"는 **확산광**을 뜻하며 직사광 역광이 아니다. **촬영 장소는 창/유리문을 등지지 않게 배치할 것.**

### 무엇이 문제였나 — 전부 배치였다

장비·소프트웨어는 무혐의였다. 세 번의 스냅샷으로 좁혔다.

| 시도 | 배치 | depth 유효화소 | 거리 중위 | 결과 |
|---|---|---|---|---|
| 1 (08-09) | 책상 위, 앉은 자세, 유리문 역광 | **21%** | 1531mm | 검출 0 |
| 2 (08-11) | **바닥에 놓임**, 문 너머 조망 | 58% | **679mm** | 촬영 불가 |
| 3 (08-11) | **1m 높이, 전신 화각 확보** | **74%** | **1858mm** | **검출 100%** |

**스냅샷으로 화각을 먼저 확인하는 절차가 결정적이었다.** 100 프레임을 돌리고 "검출 0"을 보는 것보다 훨씬 빠르다. Phase 2 촬영에서도 매 세션 첫 trial 전에 스냅샷을 확인할 것.

### DirectML 성능

8.0 fps / 지연 118ms 다. GPU 치고 느려 CPU 폴백 가능성이 남아 있으나, 본 연구는 `k4arecorder` 로 녹화 후 오프라인 처리하므로 **수집을 제약하지 않는다**(환경구축 기록 §2의 판단대로).

### 알아둘 것 — 카메라 시작이 첫 시도에 실패할 수 있다

```
usb_cmd_write(). Write command(80000001) ended in failure
colormcu_set_multi_device_mode() returned failure
-> Start K4A cameras failed!
```

이전 세션이 비정상 종료된 뒤 첫 실행에서 나타난다. **재시도하면 해결된다.** 스크립트에서 1회 재시도를 넣어두면 좋다.

### 돼지코 선택 시 주의

Microsoft 1624는 미국식 납작 2핀(Type A, 비접지)이다. 여행용 저가 어댑터는 핀을 느슨하게 물어 접점이 끊긴다.

- **소켓이 깊고 핀을 단단히 물는 제품**을 고른다. 헐렁하면 촬영 중 끊긴다
- 다이소에서 구할 수 없으면 하이마트·전자상가의 `미국형 → 한국형 변환 플러그`
- 접지형/비접지형 무관 (1624는 2핀)
- **연장선·멀티탭을 여러 단 겹치지 않는다.** 접점이 늘면 불안정해진다

### 대안 — USB-C 단독 급전 (돼지코 없이 시도 가능)

Microsoft 문서에 따르면 Azure Kinect DK는 **USB-C ↔ USB-C 케이블 하나로 전원과 데이터를 동시에 공급받을 수 있다.**

데이터 케이블의 자유단이 USB-C이고 PC 메인보드에 USB-C 3.x 포트가 있다면, 벽면 어댑터 없이 이 경로만으로 시험해볼 수 있다.

- 위험 없음. USB-C는 전압을 협상하므로 과전압이 발생하지 않는다
- 단, 소비전력 5.9W와 케이블 1.5A 요구를 만족해야 한다. 전력이 부족하면 깊이 스트림이 끊기거나 장치가 잡히지 않는다
- **이 경로로 3단계까지 통과하면 돼지코를 기다릴 필요가 없다.** 먼저 시도할 것

## 연결

**순서를 지킨다. 전원 먼저, USB 나중.**

### ① 전원

```
돼지코 → Microsoft 1624 어댑터 → 콘센트
```

Kinect 뒷면 **아래쪽 포트**(어댑터로 가는 케이블)가 전원이다.

- 확인: 본체 **전원 LED 점등**
- LED가 안 켜지면 여기서 중단. USB를 꽂지 말고 접점부터 해결한다

### ② USB

자유단 케이블을 PC의 **USB 3.0 이상** 포트에 꽂는다.

- 데스크톱 **뒷면** 포트 사용 (앞면은 내부 허브를 경유할 수 있다)
- **파란색 USB-A** 또는 **USB-C**
- **허브·연장선 금지.** 메인보드 직결
- USB 2.0(검은색)은 대역폭 부족으로 깊이 스트림이 실패한다

## 2단계 — 카메라 스트림

```bash
"C:/Program Files/Azure Kinect SDK v1.4.2/tools/k4aviewer.exe"
```

창이 열리면 `Open Device` → `Start`.

확인 항목:

- ☐ **Color** 영상 표시
- ☐ **Depth** 영상 표시 (거리에 따라 색이 변하는 화면)
- ☐ **IR** 영상 표시
- ☐ 30fps 유지, 프레임 드롭 없음
- ☐ 깊이 영상에 과도한 검은 구멍(측정 실패 영역)이 없음

| 증상 | 원인 |
|---|---|
| Color만 나오고 Depth 없음 | USB 2.0 포트 또는 전력 부족 |
| 프레임 드롭 심함 | USB 대역폭 부족. 허브 경유 여부 확인 |
| 깊이 영상 전체가 검음 | 대상이 측정 범위(0.5~3.86m NFOV) 밖 |

## 3단계 — 32 joint 획득 (G0 본체)

```bash

```

**촬영 조건**: 카메라 앞 **1.5~3m**, 전신(머리~발)이 프레임에 들어오게 서 있는다.

스크립트가 수행하는 것:

1. 설치 경로 검증
2. `initialize_libraries(track_body=True)`
3. 디바이스 시작 (Depth NFOV_UNBINNED / Color 1080p / 30fps)
4. Body tracker 시작 (GPU DirectML)
5. 100 프레임 수집 → 인체 검출률, 처리 속도, 지연 측정
6. STS 분석 대상 관절 좌표 출력 (PELVIS, NECK, NOSE, 좌우 HIP/KNEE/ANKLE/FOOT)
7. `scratch/g0_skeleton.npy` 저장

옵션:

```bash

```

**G0 통과 기준**: 스켈레톤 배열 shape 이 `(32, ...)` 이고 관절 좌표가 출력된다.

| 증상 | 원인 | 조치 |

| `start_body_tracker` 실패 | DirectML 초기화 실패 | `--cpu` 로 재시도 |
| 인체 검출 0% | 거리·프레임 문제 | 1.5~3m, 전신 프레임 확인 |
